# Measure the missing targets before adding detectors

Yes, this is worth doing, but the payoff is not where it first appears. On the engineering side it is clearly worth it: Kev can only click what the option list contains. In published desktop agents, detection failures account for most failures; **over 62% of UFO2's Windows failures were control-detection failures** ([UFO2](https://arxiv.org/html/2504.14603v2)). Native macOS AX alone does badly, with **16.9% task success versus 28.0% for OmniParser V2 and 33.7% for Screen2AX** on Screen2AX-Task ([Screen2AX](https://arxiv.org/html/2507.16704)). On the research side, the open problem is measurement, not another parser. No desktop benchmark scores whether the element list actually contains the target, no macOS dataset has human-completed element lists, and no published work patches a live macOS AX tree with vision. UFO2 merges structured and visual sources on Windows without a recall metric, and Screen2AX rebuilds the tree from pixels on macOS without merging it with live AX. The repo's own numbers change the priorities. Of 7,295 labelled targets, **84% come from AX, 4% from OCR only, one single target from the detector only, and ~9% are absent**. The OmniParser stack costs ~470 ms of detector and caption time and contributes almost nothing to labelled targets. The gaps that cost targets (Spotify, claude.ai in Arc, slow Gmail walks) look more like failures in structural access than in vision. The plan below therefore starts with a real coverage metric, then fixes AX and browser access cheaply, then makes the detector fast and macOS-trained, and only then adds a grounding fallback behind an explicit NONE choice.

## The repo's own numbers point at structure, not pixels

The 7,295 labelled voice commands over 325 Mac screens split as follows. **6,148 targets (84.3%) are covered by AX** (window or menu bar), **295 (4.0%) by OCR lines only**, **1 (0.01%) by a detector icon only**, **211 (2.9%) by the unexplained `e*` id prefix**, and **640 (8.8%) are flagged absent**. Two conclusions follow, and one important caveat.

First, the detector earns almost nothing right now. Detection at 268 ms plus captions at 203 ms is the most expensive part of perception. Even OCR (61–162 ms) and AX (111 ms median) alone already cost more than Kev's ~170 ms decision step, so the loop is bound by perception, not by the model. A source that covers one target in 7,295 does not justify ~470 ms per step at its current quality. That does not mean pixels are useless. The public evidence says vision matters most on AX-poor apps, and those are underrepresented in labels drawn from AX-heavy screens. Second, the 640 "absent" targets put a **lower bound of ~9%** on the miss rate. Kev cannot act correctly on any of them except by declining.

The caveat changes how to read everything above. The labels were written by looking at the option lists, so an element that no source produced was less likely to become a label at all. The true miss rate is higher than 9%, and it is highest on exactly the screens that motivated this work. Spotify exposes 3 AX buttons and claude.ai in Arc exposes about 1. On screens that sparse, a labeller cannot write commands for the dozens of controls a human sees, so the labels hide most of the problem. The 211 `e*` targets are also unaccounted for. Until their source is known, nobody can say whether they are a fifth source, a stale id scheme, or a bug.

Public data agrees about the scale of the problem. In a random 452-app macOS sample, **32.7% of apps had no AX, 37.8% partial and only 29.4% full coverage**, where "full" means correct boxes only and descriptions were not graded ([Screen2AX](https://arxiv.org/html/2507.16704)). In crawled apps that did work, **only 40% of elements had a correct role plus description** ([GUIrilla](https://arxiv.org/html/2510.16051v2)). GUIrilla's crawler ran on 12,298 macOS apps, and **only 1,108 produced valid trees** ([GUIrilla](https://arxiv.org/html/2510.16051v2)). So the long tail of Mac apps is largely invisible to AX-only pipelines.

## The cheapest gaps are access bugs, not perception problems

The three observed gaps each have a structural cause that is cheaper to fix than training any model.

**Arc and claude.ai: the 2-second debounce.** Chrome handles `AXEnhancedUserInterface` in `chrome_browser_application_mac.mm` and enables `kAXModeComplete | kScreenReader`, but only after a **2-second debounce**. Each new set request cancels the pending one ([Chromium source](https://chromium.googlesource.com/chromium/src/+/HEAD/chrome/browser/chrome_browser_application_mac.mm)). `AXManualAccessibility` is not handled there at all. It is an Electron-only hook, added because setting `AXEnhancedUserInterface` breaks window managers ([Electron docs](https://www.electronjs.org/docs/tutorial/accessibility)). Suppose Arc keeps Chrome's handler and the agent sets the flag on every step, or reads within 2 s of setting it. Then the agent would always see only the browser chrome, which matches the ~1 element on claude.ai. Arc's behaviour is unverified, but the test takes an afternoon: set the flag once per process, wait more than 2 s, re-walk, and never set it again.

**Gmail's 463 ms p90: per-attribute IPC.** In Chromium and Electron, each AX attribute read is a cross-process call to the renderer and costs about **10–50 ms+, compared with under 1 ms in native apps** ([cotabby #209](https://github.com/FuJacob/cotabby/issues/209)). MacOS-MCP v0.3.15 cut capture time about 10× with identical output. A heavy DOM page went **from 18.0 s to 0.83 s** and a browser-plus-system capture from **695.7 ms to ~69 ms**. Two-thirds of the gain came from unboxing `AXValue` with `AXValueGetValue` (~0.82 µs) instead of a failing `hasattr` probe (~178 µs). The rest came from `AXUIElementCopyMultipleAttributeValues`, memoised type checks, and descending into collapsed containers only when the parent has a usable bbox ([MacOS-MCP v0.3.15](https://github.com/CursorTouch/MacOS-MCP/releases/tag/v0.3.15)). The same release found that parallel prefetch inside one app was *slower*, because each app's AX server appears to handle requests one at a time. Parallelism therefore belongs across apps (menu bar vs. front window), not within one.

**Browser pages: skip the macOS AX bridge entirely.** For Chromium content, CDP's `DOMSnapshot.captureSnapshot` returns `isClickable`, which includes JS click listeners, along with bounds, paint order and whitelisted computed styles such as `cursor`, all in one call ([DOMSnapshot.pdl](https://chromium.googlesource.com/devtools/devtools-frontend/+/HEAD/node_modules/devtools-protocol/pdl/domains/DOMSnapshot.pdl)). Browser Use decides interactivity with an ordered rule set. It checks for a JS listener, native interactive tags, ARIA/AX states, `tabindex`/`on*` attributes, icon-sized elements with labels, and `cursor: pointer` ([browser-use clickable_elements.py](https://raw.githubusercontent.com/browser-use/browser-use/main/browser_use/dom/serializer/clickable_elements.py)). These rules recover exactly the div-buttons that macOS AX reports as generic groups. Nobody has published CDP latency for a Gmail-sized page, and nobody has verified whether Arc allows `--remote-debugging-port`, so both need a local check. If CDP is blocked, Chrome-family AppleScript `execute javascript` can run the same heuristic in-page.

**Spotify: a CEF host with no hook.** CEF apps respond to neither flag unless the embedder adds one. The only documented lever is relaunching with `--force-renderer-accessibility` ([AppleVis](https://mail.applevis.com/comment/78234)), which users report still leaves artists and playlists unannounced, and the report is old. Spotify's AppleScript dictionary (`playpause`, `next track`, `play track "<uri>"`) covers the playback intents directly ([spotify-applescript](https://playbooks.com/skills/openclaw/skills/spotify-applescript)). UFO2 found that API actions beat GUI actions where they exist, with o1 success rising **from 16.3% to 24.5% and average steps falling from 16.0 to 6.6** on office tasks ([UFO2](https://arxiv.org/html/2504.14603v2)). For browsing inside Spotify (search results, playlists), vision is still needed.

## Pixel detection has moved on, but nobody has timed it on a Mac

There is no OmniParser v3. Microsoft's only change after v2 is an **MIT-licensed YOLOv9-E `icon_detect_v3` (July 2026)**. The older Ultralytics-based detectors stay **AGPL** ([OmniParser repo](https://github.com/microsoft/OmniParser)), which is a licensing reason to switch regardless of accuracy. A community Core ML port ships `icon_detect_v3` with `detect_640`/`detect_1280` and Florence-2 split for the Neural Engine. It claims zero CPU/GPU fallbacks but **publishes no latency** ([1of2/omniparser-v2-coreml](https://huggingface.co/1of2/omniparser-v2-coreml)). Moving from MPS to the ANE is the most plausible large speedup, and it is unmeasured.

For desktop-specific detection, the strongest candidate is **uitag-yolo11s**. It is an 18 MB YOLO11s trained on ServiceNow's GroundCUA (~55K desktop screenshots, 3.56M human-verified boxes) and outputs 9 typed classes. It reports **R@0.5 94.0% in-distribution and 83.5% on unseen UI-Vision**. On ScreenSpot-Pro, Apple Vision alone hits 57.3% of targets (42.5% of icons). Adding the detector raises that to **90.8% (87.6% of icons)** ([uitag model card](https://huggingface.co/laywens/uitag-yolo11s-ui-detect-v1)). That OCR-plus-detector pairing is essentially the repo's pipeline, which suggests the current detector is underperforming rather than useless. The catch is that uitag needs 640-px tiles at 20% overlap. A Retina screen is roughly 24 tiles, and the full uitag YOLO step is reported at ~2.2 s on an unspecified Mac ([uitag PyPI](https://pypi.org/project/uitag/)). UI-DETR-1 beats OmniParser on the web-only WebClick (70.8% vs 58.8%) ([UI-DETR-1](https://huggingface.co/racineai/UI-DETR-1)). Salesforce's GPA-GUI-Detector has no quantitative metrics ([GPA](https://arxiv.org/pdf/2604.01676)).

Two facts reshape how to use any detector here. First, OmniParser's "interactivity" flag only records which source produced a box: YOLO boxes are `True` and OCR text is `False` ([utils.py](https://raw.githubusercontent.com/microsoft/OmniParser/master/util/utils.py)). Its detector was trained on **67k web screenshots with DOM labels and no desktop-native data** ([OmniParser paper](https://arxiv.org/pdf/2408.00203)). Second, the repo already has a free source of macOS labels. Every AX-rich screen yields role-typed boxes, which is how GUIrilla built its data ([GUIrilla](https://arxiv.org/html/2510.16051v2)). Fine-tuning a small detector on AX-derived Mac boxes plus GroundCUA targets the exact domain gap. Caption cost can be cut regardless of detector choice. Skip captions for boxes that overlap a labelled AX element, cache by crop hash, and fix OmniParser's `starting_idx` edge case, which captions one box even when every box already has OCR text ([utils.py](https://raw.githubusercontent.com/microsoft/OmniParser/master/util/utils.py)).

| Option | What it buys | Evidence | Unknown |
|---|---|---|---|
| `icon_detect_v3` via Core ML/ANE | Drops AGPL; likely large speedup | MIT, all-ANE claim ([HF](https://huggingface.co/1of2/omniparser-v2-coreml)) | Latency and macOS recall |
| uitag-yolo11s | Desktop-trained, typed classes | R 83.5% on UI-Vision; +33.5 pts target coverage over Vision OCR ([HF](https://huggingface.co/laywens/uitag-yolo11s-ui-detect-v1)) | Tiling cost; gated weights |
| Detector fine-tuned on AX-derived Mac boxes | macOS-specific interactability | GUIrilla-style labels ([GUIrilla](https://arxiv.org/html/2510.16051v2)) | Label noise (only 40% fully correct AX) |
| Screen2AX | Rebuilds tree with hierarchy | F1 43.8 detection at 0.204 s on M1 Pro; hierarchy +0.76 s ([Screen2AX](https://arxiv.org/html/2507.16704)) | Weights/licence unverified; too slow for every step |

## Hybrid lists win, but only if the selector is trained on them

The best evidence for this architecture comes from UFO2's ablation. UFO2 runs UIA first, adds OmniParser boxes with **IoU ≤ 10%** against any UIA control as pseudo-controls, and discards the rest. Between 27.9% and 56.7% of detections were duplicates ([UFO2](https://arxiv.org/html/2504.14603v2)).

| Selector | Benchmark | UIA only | Vision only | Hybrid |
|---|---|---|---|---|
| GPT-4o | WAA | 23.4% | 26.6% | 26.6% |
| GPT-4o | OSWorld-W | 22.4% | 14.3% | 22.4% |
| o1 | WAA | 25.3% | 20.8% | 27.9% |
| o1 | OSWorld-W | 24.5% | 14.3% | 28.6% |

The hybrid never loses, but **with the weaker selector the hybrid gain on OSWorld-W is zero**. Extra candidates help only a selector that can use them. That matters for Kev. Its training data contains **one** detector-only target, so the pointer head has essentially never learned to choose a detector option over a nearby AX one. Improving the detector without generating training targets that require it will probably move nothing. Any detector work has to come with relabelled or synthetic examples where the correct answer is a vision-only option.

Pure-vision grounding has improved fast. On ScreenSpot-Pro, open 7–8B models went from ~29% (Qwen2.5-VL-7B) to **58.9% (Holo2-8B) and 68.4% (UI-Venus-1.5-8B)**. At small sizes, **Holo2-4B scores 57.2 on SS-Pro and 69.4 on OSWorld-G under Apache 2.0** ([Holo2-4B](https://huggingface.co/Hcompany/Holo2-4B)), and **UI-Venus-1.5-2B scores 57.7 on SS-Pro** ([UI-Venus-1.5](https://huggingface.co/inclusionAI/UI-Venus-1.5-30B-A3B)). Grounding is still not agency: Holo1.5-3B scores 51.4 on SS-Pro but only 5.8% on OSWorld ([Holo2-4B](https://huggingface.co/Hcompany/Holo2-4B)). On a Mac, the one measured data point is Qwen2.5-VL-3B 4-bit in mlx-vlm at **3–7 s per call** ([DEV post](https://dev.to/nivdvir/building-a-real-time-screen-reader-on-macos-that-actually-works-471)). That is fine as a rare fallback and impossible as the main path. GUI-Actor's design suits Kev better. An attention head over the backbone's patch tokens gives candidate regions in one forward pass with no coordinate decoding. Training only the ~100M-param head on a frozen backbone matched prior SOTA ([GUI-Actor](https://arxiv.org/abs/2506.03143)). That works only if Kev's backbone already encodes the screenshot. If Kev reads only the serialized option list, the fallback has to be an external grounder.

Whatever grounds the fallback, the abstention decision should stay with the option list. Jedi's authors trained with refusal data and still report their model "rarely produces refusal responses". In their evaluation, refusals were absent from every model except Gemini-2.5-Pro ([OSWorld-G](https://arxiv.org/html/2505.13227v3)). AdaGround's abstention rule caught only **15 of 54** absent-target cases at a low false-refusal setting ([AdaGround](https://arxiv.org/html/2610.36874)). Kev's softmax over options plus an explicit NONE can be calibrated by temperature scaling. The 640 "absent" labels are ready-made NONE training targets. A fallback point should then be checked: snap it to a containing OCR or detector box, or hit-test it with `AXUIElementCopyElementAtPosition`, before clicking.

## The research contribution is a coverage metric, not a parser

The novelty question has a clear answer from the literature. Mind2Web scored candidate generation with Recall@K on the web (Recall@50 ≈ 90% for Dual-VCR) ([Dual-VCR](https://arxiv.org/pdf/2402.04476)). **No desktop benchmark reports whether the element list contains the target.** Screen2AX scores detectors against developer AX labels. Those labels are themselves incomplete, so a correct detection of an element missing from AX counts as a false positive ([Screen2AX](https://arxiv.org/html/2507.16704)). No published failure taxonomy separates "target absent from candidate list" from other grounding errors. And no source found quantifies how much list recall translates into task success, which is the central open question. MacPaw/UCU (Screen2AX, GUIrilla, MacArena) is the only active macOS-AX research line, and it could claim the hybrid parser angle quickly. A measurement contribution is harder to pre-empt: human-completed element lists for a few hundred Mac screens weighted toward AX-poor apps, target-coverage@K, a "target not in list" AUROC, and a correlation with downstream success. Screen2AX's own evaluation used only 166 images, so the bar for a credible dataset is a few hundred screens, not tens of thousands. Reusable gold targets already exist in GUIrilla-Gold (~1.3K human-verified macOS tasks) ([GUIrilla](https://arxiv.org/html/2510.16051v2)) and the macOS subset of ScreenSpot-Pro. MacArena's Qwen3-VL-2B/4B scores of 11.4% and 24.2% are the closest public baselines for a Kev-sized model ([MacArena](https://en.papernotes.org/ICML2026/llm_agent/macarena_benchmarking_computer_use_agents_on_an_online_macos_environment/)).

### A prioritized plan for this repo

| # | Work item | Concrete step | Exit criterion |
|---|---|---|---|
| 1 | **Coverage metric on human-completed screens** | Pick ~150–300 Mac screens stratified by app type (native, Electron/CEF, Chromium pages, pro/canvas), including Spotify, claude.ai and Gmail. For each, have a human box *every* actionable element and write commands against the screenshot, not the option list. Compute per-source and merged target-coverage (center-in-box and IoU ≥ 0.5), list precision, and per-step perception latency. Resolve what the `e*` ids are. | A number for true miss rate per app class that replaces the biased 9% |
| 2 | **Faster AX traversal** | Batch attributes with `AXUIElementCopyMultipleAttributeValues`, unbox with `AXValueGetValue`, prune into children only when the parent has a usable bbox, slice large child arrays, cache on unchanged focus with `AXObserver` as an invalidation hint only, set per-call timeouts, and walk the menu bar and the window in parallel. | Gmail p90 well under 463 ms with no node loss, checked by diff against the old walker |
| 3 | **Arc debounce check** | Set `AXEnhancedUserInterface` once per Arc process, wait > 2 s, re-walk claude.ai, and stop re-setting the flag every step. | claude.ai element count goes from ~1 to dozens, or the hypothesis is ruled out |
| 4 | **CDP / in-page DOM for browser content** | Attach via `--remote-debugging-port` or AppleScript `execute javascript`. Use `DOMSnapshot.captureSnapshot` plus the Browser Use interactivity rules, map to screen coordinates, and dedupe against AX. | Higher coverage on Chromium pages at lower latency than the AX walk |
| 5 | **App APIs for CEF holdouts** | Route Spotify playback intents to AppleScript, and test `--force-renderer-accessibility` on the current build. | Playback commands succeed without touching the GUI |
| 6 | **Detector benchmark on the Mac** | Time and score the current YOLOv8 detector, `icon_detect_v3` Core ML at 640/1280, and uitag-yolo11s (tiled, Core ML extra) on step-1 screens. Skip captions for AX-overlapping boxes and cache by crop hash. Fix the `starting_idx` bug. | Pick the detector with the best coverage gain per ms, and drop the AGPL weights |
| 7 | **AX-derived detector training data** | Export role-typed AX boxes from AX-rich screens, mix with GroundCUA, fine-tune the winner from step 6, and evaluate on AX-poor screens only. Add Kev training examples whose gold option is vision-only. | Detector-only coverage clearly above today's 1/7,295, and Kev picks those options |
| 8 | **NONE plus grounding fallback** | Train an explicit NONE option on the 640 absent labels and calibrate it with temperature scaling. On NONE, run a GUI-Actor-style head if the backbone sees pixels, otherwise Holo2-4B or UI-Venus-1.5-2B in MLX. Verify the point with a box snap or an AX hit-test before clicking. | Recovered targets on absent cases with a bounded rate of wrong clicks |

Steps 2–5 are cheap, independent, and can run alongside step 1. Each should still be scored with step 1's metric rather than with element counts. Steps 6–8 should wait for step 1, because step 1 tells you whether the remaining misses are icons (fix the detector), unlabeled text (fix OCR merging), or off-screen targets that need scrolling (no parser helps).

## Conclusion

This project is less about seeing more pixels and more about not losing what the OS already knows, then measuring what is still missing. The repo's data shows that the detector currently adds almost nothing per millisecond. The worst gaps trace to a debounce timer, per-attribute IPC and a CEF host with no accessibility hook, and none of those needs a new model. Once structural access is fixed, vision becomes a targeted filler for AX-poor apps, and it pays off only if Kev is trained on examples where the vision option is the correct answer. The small-selector result from UFO2 is the warning to heed.

The most valuable output is the measurement itself. A target-coverage metric on human-completed Mac screens, linked to task success, is publishable, hard for faster-moving labs to pre-empt, and decides every later engineering choice in this plan. The main uncertainty is whether better list recall actually raises task success for a sub-1B selector. Nobody has measured that, and this repo is set up to be the first to do so.
