# Ask apps for actions before probing pixels

The most useful new option sources for Kev are app-level semantic channels and caches built from data the project already has. Interaction probing and new Apple vision frameworks help less. **Spotify's AppleScript dictionary already exposes the playback verbs its 3 AX buttons hide**, and an in-process Apple Event costs about **11 ms** on the owner's Mac. For Arc pages with no AX web area, the realistic fix is a browser extension content script, because Chrome 136+ blocks CDP on the default logged-in profile. For speed, the explorer's 2,835 states and press transitions support a per-screen element memory and a crop-hash caption cache, which could remove most of the ~470 ms detector-plus-caption cost on revisited screens. Probing the live UI (hit-tests, cursor shape, hover diffs, Tab traversal) works mainly as verification. A targeted AX hit-test is cheap and safe enough to confirm or enrich detector boxes. Cursor and hover probing are slow, need the window frontmost, and have visible side effects. Apple's 2025–2026 frameworks add no public UI-element detector, and the onscreen-entity APIs feed only Siri. One caveat governs everything below: a small selector gains from new option types only when its training data includes targets of those types. UFO2's weaker model gained nothing from its hybrid list, and agents that are offered tools invoke them only about a third of the time.

## The gaps call for different kinds of fix

Kev picks one id from a list built from the AX window and menu bar (~84–87% of real targets), Apple Vision OCR (~5%) and an OmniParser-style detector (~11% by eye, ~470 ms including captions). The three known gaps differ in kind. Spotify is a CEF app whose web content barely reaches AX, but its intents are few and well known (play, skip, shuffle). Arc pages with no AX web area are a browser bridge failure that hits about half of the Canvas and Calendar screens, where the DOM is fully present. Icon-only buttons are a naming problem: the element often exists somewhere, but it has no usable label. A method that fixes one gap usually does nothing for the others. The sections below sort methods by what they add: options for GUI elements, non-GUI actions offered as options, or speed for the sources that already exist.

## Live probing verifies candidates but rarely discovers them

**AX hit-testing is the one probe worth adopting.** `AXUIElementCopyElementAtPosition` returns the deepest accessible element at a screen point ([Apple AXUIElement.h](https://leopard-adc.pepas.com/documentation/Accessibility/Reference/AccessibilityLowlevel/AXUIElement_h/CompositePage.html)). One developer measured **64–70 ms per hit-test** on a Chromium-heavy simulator surface and **~10 ms p50 per lookup** on a native AppKit sidebar in the same app, a more than 5x spread ([locant PR #78](https://github.com/Malik1942/locant/pull/78)). Another replaced a 124 ms tree walk with a single cached-position hit-test that took about 2 ms ([remote-mic-app PR #851](https://github.com/HD838A/remote-mic-app/pull/851)). At these costs a dense grid scan takes seconds, but probing the 5–40 detector or OCR boxes that match no AX node is affordable. Each probe either attaches a real role, title and `AXPress` to a pixel detection or rejects it, which is the verification step the earlier plan proposed for grounding fallbacks. Chromium routes hit-tests through its own code path, including a redirect for remote app shims ([Chromium ax_platform_node_mac.mm](https://chromium.googlesource.com/chromium/src/+/913eaefa55beab765aa1d99da170db474d8c63ca/ui/accessibility/platform/ax_platform_node_mac.mm)). That makes it plausible that hit-tests reach nodes the child walk prunes, but no source confirms it. On Spotify the probe most likely returns the same container group, so test it before counting on it.

**Cursor-shape probing and hover diffs are slow, visible and unproven.** `NSCursor.currentSystem` reports whichever cursor is showing ([Apple docs](https://developer.apple.com/documentation/appkit/nscursor/currentsystem)). Developers report that it is deprecated in macOS 15 ([Apple forums](https://developer.apple.com/forums/thread/760305)) and that equality checks against the pointing-hand cursor are unreliable, so you have to compare images ([SO 41241736](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/41241736/how-to-detect-current-system-cursor-on-osx)). The cursor only changes for the app under the real pointer, so each probe moves the user's mouse and waits for a frame. Background mouse events are unreliable: one report says `postToPid` delivered only keyboard events ([SO 75511477](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/75511477/how-to-post-to-event-to-specific-window-on-macos)), and even tools that post mouse events silently warn of normal side effects in the target ([silentmouse](https://github.com/ph0ryn/silentmouse)). Desktop GUI rippers discover widgets from toolkit metadata, not hover diffs ([Memon, WCRE 2003](https://www.cs.umd.edu/~atif/pubs/MemonWCRE2003-abstract.html)). No desktop tool or paper was found that uses cursor shape or hover diffs to find widgets. The pointer cursor is the main clickability cue in web content, so a single-target cursor probe could settle "is this Arc icon a button?". Treat that as a disambiguation step, not an enumeration source. Read `AXHelp` before hovering for a tooltip; it is cheaper (unverified).

**Keyboard focus traversal and Voice Control add nothing for these gaps.** With macOS's default setting, Tab moves only between text fields and lists ([a11yproject](https://a11yproject.com/posts/macos-browser-keyboard-navigation)). Traversal also changes focus, which can scroll pages or commit text. Apple describes Voice Control's "Show numbers" as labelling clickable items, with a numbered grid as the fallback for unlabeled elements ([Apple Voice Control brief](https://apple.com/accessibility/pdf/Voice_Control_Tech_Brief_Sept_2019.pdf)). That wording implies it reads the same AX data, so it would miss what Kev misses. It also has no public API. A one-minute check ("show numbers" in Spotify and Arc, then count) would settle it.

**Two sources do add new elements: a browser extension and learned interactability.** An MV3 content script with a `MutationObserver` can export a page's interactive elements over native messaging from the user's real Arc or Chrome profile. CDP cannot do this, because Chrome 136+ ignores `--remote-debugging-port` on the default user-data-dir ([Chrome for Developers](https://developer.chrome.com/blog/remote-debugging-port)), and the restriction persists in Chrome 151 ([cua #2916](https://github.com/trycua/cua/issues/2916)). Arc still runs Chrome extensions but has been in maintenance mode since 2025 ([Wikipedia: Arc](https://en.wikipedia.org/wiki/Arc_(web_browser))). The extension can apply the same Browser Use interactivity rules the earlier report recommended for CDP ([browser-use clickable_elements.py](https://raw.githubusercontent.com/browser-use/browser-use/main/browser_use/dom/serializer/clickable_elements.py)), and it does not depend on Arc's AX bridge. For Electron apps the picture differs. **On the owner's Mac, `@electron/fuses` shows Slack and Notion with Node inspect, `RUN_AS_NODE` and `NODE_OPTIONS` all disabled and ASAR integrity on. VS Code has all three enabled. Spotify is CEF, not Electron.** Electron's fuses do not gate `--remote-debugging-port` ([Electron fuses](https://www.electronjs.org/docs/latest/tutorial/fuses)), so relaunching with that flag probably yields CDP access. That is unverified per app, it interrupts the user, and it opens a localhost port with full session access.

Learning interactability from outcomes has strong precedent. Apple's Never-ending UI Learner labelled tappability by tapping elements and checking whether the screen changed, across more than 500,000 actions in 6,000 apps, and trained tappability and screen-similarity models on those labels ([arXiv 2308.08726](https://arxiv.org/abs/2308.08726)). The explorer's press transitions are the same signal. Label a press positive if it produces an AX or pixel diff and negative if nothing changes, then fine-tune the detector on those labels. This avoids the noise of metadata-derived labels, which PixelWeb documents in WebUI ([arXiv 2504.16419](https://arxiv.org/html/2504.16419v2)). Passive logging of the user's own clicks extends the idea to AX-blind apps. On Android, 20M+ logged clicks predicted the next tap at 71% top-3 ([arXiv 2108.05342](https://arxiv.org/abs/2108.05342)), but no macOS system of this kind exists, and the logs are privacy-sensitive.

## Non-GUI channels cover Spotify and Apple apps, not Electron

**AppleScript is the most practical channel for the apps where AX is thinnest.** These dictionary counts were measured directly on the owner's Mac with `sdef`. **Spotify exposes 6 commands (`next track`, `previous track`, `playpause`, `pause`, `play`, `play track`), Music 31, Finder 25, Chrome 23, Mail 19, Arc 10, Safari 10, Calendar 8, and Slack, VS Code, Notion, Obsidian, Discord and Raycast 0.** Command counts understate what the dictionaries can do, because settable properties such as Spotify's shuffling, volume and player position are actions too. Mail's dictionary has no archive verb; the usual form moves the message to a mailbox. Latencies were also measured on the owner's Mac. **An `osascript` call took 130–170 ms, mostly process spawn, while 20 Apple Events from one JXA process averaged 11.45 ms each.** Keep one long-lived sender process. **From the terminal, `tell application "Spotify"` failed with error -1743**: Automation consent is per sender-target pair, so Kev's host process needs a one-time grant for each app. An existing MCP server wraps this pattern and warns about the same first-run prompts ([macos-automator-mcp](https://github.com/steipete/macos-automator-mcp)). Spotify's dictionary cannot like a song or add to a playlist. Those need the Web API, which since February 2026 limits new Development Mode apps to Premium accounts and 5 users ([Spotify developer blog](https://developer.spotify.com/blog/2026-02-06-update-on-developer-access-and-platform-security)).

**App Intents have a ready-made local catalog, but the apps that matter here do not use them.** On the owner's Mac, the ToolKit database at `~/Library/Shortcuts/ToolKit/Tools-prod.v79-*.sqlite` lists **2,163 tools from 104 bundles**, with localized titles, parameter types, enum cases, search keywords and sample phrases. That is close to a ready-made retrieval index for voice commands. Coverage per app on the same Mac was **Notes 57, Reminders 51, Safari 42, Mail 32 (including `ArchiveMessageIntent`), Calendar 24 and Music 12. Spotify, Slack, Chrome, Arc, Notion, Discord, Obsidian and VS Code have none.** Apple positions App Intents and the new App Schemas as the structured way for apps to declare actions to Siri ([WWDC26 session 240](https://developer.apple.com/videos/play/wwdc2026/240/)). Beta code laid groundwork for MCP on top of them ([9to5Mac](https://9to5mac.com/?p=1020830)), but nobody has confirmed that it shipped. The obstacle is invocation. **The `shortcuts` CLI on the owner's Mac can only `run`, `list`, `view` and `sign` user shortcuts by name (`list` took 36 ms). It cannot call a raw intent.** Wrapping each wanted intent in a generated, signed shortcut works, but the user must import it. The ToolKit schema is private and versioned (`v79`).

**The menu bar is already in the list and is still underused.** Kev's option list includes the menu bar, so commands like Spotify's Playback menu items, if that menu exists in the current build (unverified), should already be pressable through AX without touching the window. The open questions are whether those items are in the labels and whether Kev picks them. The notes found no measurement of menu-walk latency or per-app item counts. A quick local benchmark would answer both.

The evidence that semantic actions help agents is consistent. In UFO2, adding APIs raised o1's success on office tasks from **16.3% to 24.5% and cut steps from 16.0 to 6.6** ([UFO2](https://arxiv.org/html/2504.14603v2)). OSWorld-MCP reports Claude 4 Sonnet rising from **38.9% to 45.0%**, but the best tool invocation rate was only **about 33–36%** ([arXiv 2510.24563](https://arxiv.org/abs/2510.24563v2)). An aggregator reports MCPWorld's MCP-only agents at 53.2% against 70.7% for GUI-only and 75.1% for hybrid ([Emergent Mind](https://api.emergentmind.com/topics/hybrid-gui-api-action-space)). Semantic actions should therefore enter Kev's list as ordinary options next to AX elements, with training examples where they are the gold answer, rather than run as a separate mode.

## Caching and temporal reuse attack the 470 ms, not coverage

The caching ideas below do not find new targets. They make the expensive sources cheap enough to run every step. **ScreenCaptureKit reports per-frame `dirtyRects`** on a live stream ([Apple docs](https://developer.apple.com/documentation/screencapturekit/scstreamframeinfo/dirtyrects.md)). That allows a simple rule: keep detections whose boxes do not touch a dirty rect, and re-run the detector only on changed tiles. Nobody has published how reliably browsers populate it. Recent agent papers show the size of the prize for VLM computation. GUIFlow's patch-diff KV reuse cut per-step latency **1.94–2.55x** ([arXiv 2610.34959](https://arxiv.org/html/2610.34959)). PastForward predicts the next screen from stored transitions and precomputes while the action plays out, for **1.63–2.36x** edge speedups at equal success ([arXiv 2609.32166](https://arxiv.org/html/2609.32166v1)). No paper measures detector or caption caching for GUI agents. Captions are about 200 ms of the 470 ms, so a cache keyed by perceptual hash of each crop, which reuses captions for repeated icons, is the obvious first test. The 712 explorer screenshots include revisits, so hit rates can be measured offline.

A per-screen element memory goes further. AutoDroid explores apps, builds a UI transition graph and has an LLM write a function table for each element ([arXiv 2308.15272](https://arxiv.org/abs/2308.15272)). AppAgentX's page-node memory raised task success from **16.9% to 70.8%** ([arXiv 2503.02268](https://arxiv.org/abs/2503.02268v2)). Keyed by an AX-tree fingerprint or screen hash, the explorer log could store the union of elements confirmed by press transitions on each screen, then merge them into the live list on a revisit and skip detection for known crops. Those papers report task success, not element recall, so the coverage gain has to be measured here. AXObserver notifications (`AXLayoutChanged`, `AXFocusedUIElementChanged`, and others) work as dirty flags. Tiling window managers already register them per app ([paneru](https://docs.rs/crate/paneru/latest/source/src/platform.rs)), so the agent can re-walk during idle time instead of after the user speaks. No source reports how reliably Chromium emits them, so treat them as hints, not a complete source.

Apple's new frameworks fit as cheaper parts, not new sources. Vision's `RecognizeDocumentsRequest` returns structured text, tables, lists and data detectors (phone numbers, emails, addresses) ([WWDC25 #272](https://developer.apple.com/videos/play/wwdc2025/272/)). That could tag links and table cells inside canvas-rendered pages. The roughly 3B on-device Foundation Model is multimodal ([Apple tech report 2025](https://machinelearning.apple.com/research/apple-foundation-models-tech-report-2025)), and the WWDC26 cycle added image input ([MacRumors](https://www.macrumors.com/2026/06/09/apple-outlines-major-ai-and-developer-tool-updates/)). It could replace Florence-2 for icon captions if one batched call is fast, but no latency figures exist. `NSUserActivity.appEntityIdentifier` exposes onscreen content only for apps that adopt it, and only to Siri and Apple Intelligence ([Apple docs](https://developer.apple.com/documentation/foundation/nsuseractivity/appentityidentifier.md)). Mac users were still asking for iOS-style Screen Recognition in VoiceOver in October 2026 ([AppleVis](https://www.applevis.com/comment/218666)). General VLMs asked to list every interactive element reach only about **0.13 F1** ([GUI-360°](https://arxiv.org/pdf/2511.04307)), so they belong in offline labelling, not the runtime loop.

## A prioritized plan for this repo

The order follows coverage gained per unit of effort, and each step should be scored with the target-coverage metric from the earlier plan, not by counting elements. **First**, add an AppleScript option source. Parse `sdef` once per app version, turn each verb or writable property into a templated option ("Spotify: next track"), keep one JXA process alive, grant Automation to Kev's host for Spotify, Music, Mail and Finder, and add training examples where these options are the gold answer. In the same pass, check whether Spotify's menu bar items appear in current labels. **Second**, run AX hit-tests on every detector and OCR box that has no AX match. Set `AXUIElementSetMessagingTimeout` to cap hung calls, use the result to add role and action or to drop the box, and log how often a hit-test returns a node the walk missed. **Third**, test caching offline on the 712 explorer screenshots: crop-hash caption hits, then a per-screen element memory keyed by AX fingerprint. Both pay off if revisit hit rates are high, and both need no new permissions. **Fourth**, build the Arc/Chrome content-script extension with native messaging, since it is the one method that plausibly closes the largest structural gap (about half of the Canvas and Calendar screens). **Fifth**, turn the explorer's press transitions into tappability labels and fine-tune the detector, following the Never-ending UI Learner. Defer App Intents until the target app list includes more Apple apps. Defer CDP relaunches of Electron apps until the user wants Slack or Notion coverage. Skip cursor, hover and Tab probing, Voice Control and VLM element listers as discovery sources.

## Conclusion

The earlier research framed the problem as recovering GUI elements that AX loses. This round suggests the cheaper move is often to stop needing those elements. For a voice agent, "skip this song" has the same meaning whether it reaches Spotify through a hidden button or an Apple Event. The local measurements show the channel exists exactly where AX fails for media and Apple apps, and is missing for Electron, where the content-script and CDP routes take over. The structural risk shifts from detection to selection. Every new source adds options a 0.8B selector has never seen chosen, and the hybrid-agent literature shows both that tool options go unused and that weak selectors gain nothing from richer lists. The decisive experiment is therefore not another detector. It is relabelling a slice of the explorer data so that AppleScript, hit-test-verified and extension-derived options appear as gold targets, then measuring whether Kev's pick accuracy and coverage rise together.

Two things remain unknown and are cheap to settle on the owner's Mac: whether hit-tests surface Chromium or CEF nodes the child walk misses, and what share of explorer screens are revisits whose captions and elements could come from a cache. Both answers decide how much of the ~470 ms perception budget can be removed, which matters as much as coverage for a ~170 ms decision model.
